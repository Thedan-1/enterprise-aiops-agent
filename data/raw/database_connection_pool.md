# 数据库连接池（HikariCP）故障排查

## 连接池的基本原理

应用不会为每次数据库查询新建一个物理连接（建连开销大），而是维护一个连接池，请求来了从池里借一个连接，用完还回去。连接池有一个最大连接数上限（maximumPoolSize）。

## 连接池耗尽的典型症状

- 应用日志出现 `Connection is not available, request timed out after 30000ms` 或类似字样
- 应用响应时间显著上升，但数据库自身的 CPU/QPS 看起来并不高（这是关键区分信号——如果数据库本身也在高负载，是数据库慢；如果数据库空闲但应用连接池耗尽，是应用侧的问题）
- 新请求大量排队等待可用连接，超过 `connectionTimeout` 后请求失败

## 常见根因

1. **慢查询占用连接不释放**：某个查询因为缺索引或锁等待跑得很慢，连接被长时间占用，池子里可用连接越来越少
2. **连接泄漏**：代码里获取连接后某个异常分支没有正确 close/归还连接（try-with-resources 缺失是常见原因）
3. **下游依赖变慢导致事务时间变长**：如果在一个数据库事务内还调用了外部服务（反模式，但现实中常见），外部服务变慢会直接拖长连接占用时间
4. **瞬时流量突增**：正常流量下连接数够用，突发流量下不够用

## 排查步骤

1. 查看连接池监控（活跃连接数 active / 空闲连接数 idle / 等待队列长度）
2. 查看数据库慢查询日志，确认是否有异常耗时的SQL
3. 检查代码里是否存在"在事务内调用外部HTTP请求"这种反模式
4. 检查最近的流量曲线，排除纯粹的流量突增

## 修复方向

- 短期：适当调大连接池上限（treat symptom, not root cause，不能作为唯一手段）
- 中期：给慢查询加索引，拆分长事务
- 长期：避免在数据库事务内调用外部服务；对下游依赖增加超时和熔断，防止级联拖垮连接池
