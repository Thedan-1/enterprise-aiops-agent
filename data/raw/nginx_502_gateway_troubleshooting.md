# Nginx 502/504 网关错误排查指南

## 什么是502 Bad Gateway

502 表示 Nginx（作为反向代理/网关）从上游服务（upstream）收到了无效响应，或者上游连接在响应过程中被意外关闭。502 是网关层面的错误，通常不是客户端的问题，而是网关到后端服务这一段链路出了问题。

常见原因排序（按出现频率）：
1. 上游服务（后端应用）进程崩溃或重启，Nginx 连接的是一个已经不存在的进程
2. 上游服务响应超时，Nginx 主动断开连接（配合504一起出现）
3. 上游服务返回了不符合 HTTP 协议规范的响应头
4. 上游服务的连接池耗尽，无法接受新连接，直接拒绝或重置连接（connection reset）
5. Nginx 与上游之间的网络问题（常见于跨机房/跨可用区调用）

## 什么是504 Gateway Timeout

504 表示 Nginx 在 `proxy_read_timeout` / `proxy_connect_timeout` 配置的时间内没有收到上游响应。504 和 502 经常成对出现：先是若干次504（说明上游变慢），随后因为上游连接堆积导致连接池耗尽，进而触发502。

## 排查步骤

1. 查看 Nginx error.log，确认是 `upstream prematurely closed connection` 还是 `upstream timed out`，两者指向的原因不同
2. 查看上游服务自身的日志（这一步很关键——Nginx日志只能告诉你"连接失败"，不能告诉你"为什么失败"，必须结合后端服务日志）
3. 查看上游服务的实时指标：CPU、Memory、连接池使用率、GC频率
4. 如果是连接池耗尽，检查数据库/下游依赖服务是否也在变慢（连接池耗尽往往是下游变慢的连锁反应，而不是根因）
5. 检查最近是否有发布/配置变更

## 与"连接池耗尽"关联的典型链路

`下游服务响应变慢` → `当前服务处理请求耗时变长` → `请求堆积，连接池里的连接迟迟不释放` → `连接池耗尽，新请求排队或直接拒绝` → `Nginx 收不到及时响应或收到连接重置` → `502/504`

这是一个级联故障（cascading failure）的典型模式：根因往往在链路的最下游，但最先被用户感知到的是最上游网关的错误码。
