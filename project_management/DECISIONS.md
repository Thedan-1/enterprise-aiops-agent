# V2 决策记录

## V2-001：公开仓库使用 PR，而非直接覆盖 main

- 原因：保留审查轨迹，便于面试时展示变更范围、测试和权衡。
- 替代：直接推 main，步骤少但缺少工程审查过程。

## V2-002：认证与多租户先做可运行的本地演示实现

- 原因：当前 Docker/PostgreSQL 尚未可用，但安全边界必须先能演示和测试。
- 方案：离线应用使用签名 Token、确定性 RBAC、tenant scope 和 JSONL 审计；生产路径保留数据库模型演进设计。
- 何时替换：接入 PostgreSQL 后将用户、租户与审计迁入数据库，Token 换为标准 OIDC/OAuth2 Provider。

## V2-003：工具只读

- 原因：诊断场景不需要删除、重启、修改配置。OWASP 将过度功能、过度权限和过度自主列为 Agent 高风险来源。
- 结果：即使 Prompt Injection 成功影响 Planner，也没有破坏性工具可调用；权限仍由代码校验，不由 LLM 决定。

## V2-004：服务名使用显式别名表，不做模糊猜测

- 原因：用户会说“订单服务”，监控系统使用 `order-service`。若不规范化，工具会误报无数据；若使用模糊匹配，又可能把请求路由到错误的生产服务。
- 方案：在 Tool 边界维护小型、可审查的中文名/英文名 allowlist，日志和指标工具共用规范名称。
- 替代：让 LLM 始终输出英文服务名；真实回归已证明不可靠。使用编辑距离或向量匹配；服务误路由风险高于便利性。
- 何时改变：接入 CMDB/Service Catalog 后，由权威服务目录提供别名、租户作用域和生命周期状态。

## V2-005：重试只覆盖瞬时失败，最终失败返回结构化降级

- 原因：Tool 或 LLM 的 429、5xx、网络超时可能短暂恢复，但参数错误和代码异常通常不会因重试消失。
- 方案：Tool 只重试显式 `TransientToolError` 与超时；DeepSeek 只重试 429、5xx 与网络超时，最多 3 次，指数退避。Agent 各 LLM 阶段最终失败时返回 `status=error`、零置信度和人工升级提示。
- 替代：所有异常统一重试会放大故障并隐藏 bug；完全不重试会降低瞬时故障成功率；无限重试会突破总延迟预算。
- 已知边界：同步 Tool 的线程超时能让 Agent 返回，但底层不可取消的阻塞调用可能短暂继续运行。生产适配器仍需设置客户端级连接/读取超时。
- 何时改变：多实例部署后引入共享 Circuit Breaker；只有实测连续失败和恢复窗口证明需要时再增加。
